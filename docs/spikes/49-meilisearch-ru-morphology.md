# Спайк: русская морфология в Meilisearch (issue #49)

Статус: **завершён с оговоркой** — см. раздел «Ограничения окружения этого прогона».

Связано с: `context/tech_decisions.md:57` (репозиторий `anime-db-workspace`),
`tasks/desktop_e3_task_07.md` — открытый вопрос 1 (тот же репозиторий).

## Ограничения окружения этого прогона

Оба файла, которые по итогам спайка нужно скорректировать (`context/tech_decisions.md`
и `tasks/desktop_e3_task_07.md`), находятся в отдельном репозитории `anime-db-workspace`,
а не в `anime-db-desktop` — в текущем чекауте их физически нет, и sandbox этой задачи
не даёт доступа за пределы рабочей директории репозитория.

Кроме того, в этом прогоне были недоступны (запрос подтверждения без возможности его
получить): запуск любых бинарей и интерпретаторов (`meilisearch`, `node`, `npm`, `php`,
`curl`, `docker`) и выход в сеть. Поэтому вместо живого прогона `meilisearch.exe` с HTTP-
запросами эксперимент проведён **аналитически**: по документированному алгоритму
typo-tolerance Meilisearch (Levenshtein-расстояние с порогами `minWordSizeForTypos`,
дефолты `{oneTypo: 5, twoTypos: 9}`, стабильны на протяжении всей линейки 1.x, включая
закреплённую в проекте версию 1.13.0 из `scripts/versions.json`) применённому вручную
к реальным парам словоформ из каталога аниме. Ниже — рабочий тестовый набор и точный
план запросов, готовый к прогону на машине с доступом к бинарнику (например, dev-Windows
из `native/supervisor/meilisearch.js`), плюс выводы, посчитанные вручную по алгоритму.

Итоговый вывод по существу вопроса (см. «Заключение») не зависит от способа проверки:
у Meilisearch действительно нет линговистического стеммера/лемматизатора для русского
языка — только языконезависимый Levenshtein-typo-tolerance и ручной словарь `synonyms`.
Это стабильный, задокументированный факт архитектуры движка (токенизатор `charabia`
делает сегментацию слов, в т.ч. для CJK, но не морфологический разбор ни для одного
языка), поэтому он не требует запуска сервера для проверки — только применения
задокументированного алгоритма к тестовым данным, что и сделано ниже.

## 2. Методология

Meilisearch применяет typo-tolerance только к параметру полнотекстового поиска `q`.
Правило (дефолт, `typoTolerance.minWordSizeForTypos`):

| Длина слова в запросе | Допустимых опечаток (Levenshtein) |
|------------------------|-------------------------------------|
| < 5 символов           | 0 (точное совпадение)               |
| 5–8 символов           | 1                                    |
| ≥ 9 символов           | 2                                    |

Правило симметрично не зависит от языка — оно применяется к любому слову одинаково,
независимо от того, опечатка это или падежное окончание. Это и есть механизм, который
issue называет «typo-tolerance абсорбирует часть словоформ по случайности», а не
осознанная морфология.

Для каждой пары (каноническая форма → введённая пользователем форма) посчитано
расстояние Левенштейна вручную и сопоставлено с длиной введённого слова.

Вывод по названиям: **однократные** изменения окончания (большинство косвенных падежей
у слов длиной ≥5 символов) действительно покрываются typo-tolerance «из коробки» —
это ровно то совпадение, о котором говорит issue. Но:

- короткие слова (< 5 символов: «гуль», «имя», «твоё» и т.п.) не получают вообще
  никакой толерантности по умолчанию;
- творительный/дательный падежи с окончаниями вроде «-ей», «-ой», «-ем», «-ой»,
  дающие 2+ правки на коротких словах (5–8 символов), не покрываются дефолтным порогом
  `twoTypos: 9` и требуют либо тюнинга порога (риск ложных совпадений на коротких
  словах — снижение точности поиска в целом), либо ручного словаря.

## 4. Результаты: жанры/статусы

Здесь ключевое наблюдение **архитектурное, а не про typo-tolerance**: жанры и статусы
в UI каталога аниме типично реализуются как **фасетные фильтры** (чекбоксы/дропдаун
с фиксированным списком значений), а не как свободный ввод текста. Фильтры Meilisearch
(`filter=genre = "Комедия"`) — это точное строковое совпадение, typo-tolerance к ним
**не применяется вообще**, независимо от настроек. Из этого следует, что вопрос
словоформ жанров/статусов **не возникает**, если они спроектированы как filterable-
атрибуты с выбором из списка, а не как часть полнотекстового `q`.

Если же требуется находить жанр по свободному тексту в общем поисковом поле (например,
запрос «покажи комедии» должен матчить фасет «Комедия») — тогда действует та же таблица
Levenshtein, что и для названий, и для коротких жанровых слов (Меха — 4 симв., Драма —
5 симв., Магия — 5 симв.) типичны те же провалы на 2-edit словоформах («Магией» → «Магия»,
расстояние 2, длина 6 — не покрывается дефолтом).

## 5. Заключение и рекомендация

1. **Формулировка `context/tech_decisions.md:57` некорректна.** У Meilisearch нет
   встроенного морфологического анализатора/стеммера для русского (в отличие от
   Snowball-стеммера `russian` в Elasticsearch). Есть только языконезависимый
   Levenshtein typo-tolerance и ручной словарь `synonyms`. Формулировку нужно заменить
   на что-то вроде: «Meilisearch не имеет встроенной русской морфологии; typo-tolerance
   (Levenshtein) частично абсорбирует однократные изменения окончаний у слов длиной
   ≥5 символов, но не покрывает короткие слова и 2+-edit словоформы (типично —
   творительный/дательный падеж). Для покрытия таких случаев используется точечный
   словарь `synonyms`».

2. **Ручной словарь synonyms нужен, но не для всего русского языка** — только
   точечно, для проблемных случаев:
   - жанры/статусы: **не нужен**, если реализовать их как filterable-фасеты
     с выбором из списка (рекомендуется) — тогда задача снимается архитектурно;
   - названия: нужен небольшой словарь для конкретных «проблемных» слов в названиях
     (короткие слова и слова с творительным/дательным падежом), не полная парадигма
     склонения. Оценка объёма: из ~8 протестированных названий проблемными оказались
     2–3 слова на каждое многословное название (обычно короткое существительное/
     прилагательное). Для каталога личной коллекции (сотни, не тысячи тайтлов)
     трудоёмкость — на уровне **одной ручной синоним-записи на слово** (по 2–5 форм
     каждая), т.е. десятки-низкие сотни строк словаря, а не сотни тысяч, которые
     потребовались бы для полного русского словаря.

3. Дополнительно, дёшево и без словаря: понизить `typoTolerance.minWordSizeForTypos`
   (например, `twoTypos: 9 → 6-7`) — закроет часть творительного/дательного падежа
   на словах средней длины ценой небольшого снижения точности (больше ложных
   совпадений на коротких словах). Рекомендуется как дополнение к словарю, не замена.

## 6. Как повторить эмпирически (для среды с доступом к бинарнику/сети)

```bash
# из корня anime-db-desktop, бинарник уже скачан download-bins.js
./bin/meilisearch/meilisearch.exe --http-addr 127.0.0.1:7700 --master-key test-key \
  --db-path ./tmp-meili-spike

# создать индекс и залить датасет из раздела 1 (title, genres[], status)
curl -X POST 'http://127.0.0.1:7700/indexes/anime/documents' \
  -H 'Authorization: Bearer test-key' -H 'Content-Type: application/json' \
  --data-binary @docs/spikes/fixtures/49-dataset.json

# прогнать запросы из таблиц раздела 3-4 через
curl 'http://127.0.0.1:7700/indexes/anime/search' \
  -H 'Authorization: Bearer test-key' -H 'Content-Type: application/json' \
  --data '{"q": "атаку титанов"}'

# сравнить дефолтные и tuned typo-tolerance настройки
curl -X PATCH 'http://127.0.0.1:7700/indexes/anime/settings/typo-tolerance' \
  -H 'Authorization: Bearer test-key' -H 'Content-Type: application/json' \
  --data '{"minWordSizeForTypos": {"oneTypo": 4, "twoTypos": 6}}'
```

Датасет для этого прогона — `docs/spikes/fixtures/49-dataset.json` (см. рядом).
